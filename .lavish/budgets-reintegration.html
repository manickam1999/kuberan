What the findings imply

1

UI-only, low risk

Hook, types, and api-client compile unchanged. No backend change is required to restore a page — the hardening below is quality work, not a blocker.

2

The model lies about dates

StartDate / EndDate are stored but never read. Progress is derived purely from time.Now(). The real feature is a recurring monthly/yearly cap.

3

is_active is decorative

Forced true on create, not updatable, ignored by progress. The only way to stop a budget is to delete it. The old UI showed a toggle that did nothing.

4

N+1 baked into the UX

Old page fired one progress request per card; the bot loops too. A batch endpoint should land before the UI is rebuilt, not after.

5

Expense categories only

Progress sums type='expense' only, so a budget on an income category is always 0% spent. The picker must filter to expense types.

6

Empty DB = fix-it window

Zero budgets exist. Schema flaws (dead columns, no uniqueness, no CHECK) are cheap to fix now and expensive once real budgets land. Take the window.

Design decisions

recommendations
# Decision Recommendation Why
D1 Date-range vs recurring Drop date columns, keep period Columns never affected behavior; makes the model truthful, form simpler. Reversible.
D2 is_active Make updatable + pause toggle Turns a dead field into a real feature; stop a budget without losing history.
D3 Batch progress Add GET /budgets/progress Kills the N+1 for page, dashboard card, and bot in one call.
D4 Uniqueness One active / category + period Removes ambiguity for rollups; matches intuition ("my monthly Food budget").
D5 Sub-category rollup Defer + document No nested expense categories exist today. Revisit if nesting is used.
D6 Category picker scope Expense only Income budgets are always 0% spent by construction.
D7 Dashboard presence Compact budgets card What makes budgets get used daily — likely why the page died the first time.
D8 Over-budget display Cap bar, show "over by X" Percentage can exceed 100 and remaining can go negative by design.
Key fork · D1

Recurring caps vs. date-ranged budgets

Option A — Recurring (recommended) simpler

Drop the date columns. A budget is a monthly/yearly cap per category. Progress already works this way.

  • 1 migration, form drops to 4 fields
  • Model tells the truth
  • Matches how you'd track spending
Option B — Date-ranged more code

Make progress honor Start/End, add a custom period for one-off budgets.

  • New concept + window logic
  • Only worth it if custom ranges are a real want
  • Larger test surface
